# Authentication Domain

Status: **implemented (A-001 persistence foundation).** This document describes
the authentication data model only. No auth endpoints, token issuance, password
hashing, email, or OAuth flows are implemented yet.

## Core boundary: User != Customer

`User` is an **authentication identity**: "who are you?". It is deliberately not
the e-commerce `Customer` aggregate. `User` must never grow address, company,
delivery-preference, order-history, loyalty, or customer-commerce fields.

A future `Customer` domain may link to a `User` (for authenticated checkout and
account features), but that is a separate task. This separation keeps room for:

- guest checkout (orders exist without a `User`);
- authenticated customers;
- multiple delivery addresses;
- B2B accounts;
- guest-to-account conversion;
- orders independent of login identity.

Authorization (roles/permissions) is also out of scope; authentication answers
identity, authorization is separate and is added only when a real requirement
exists.

## Models

### User

| Field             | Notes                                                |
| ----------------- | ---------------------------------------------------- |
| `id`              | UUID v7 (time-ordered), generated by the client      |
| `email`           | Original usable email value, preserved as provided   |
| `emailNormalized` | Deterministic normalized email; **unique**           |
| `emailVerifiedAt` | `null` = unverified; set = verified (explicit state) |
| `createdAt`       | Creation timestamp                                   |
| `updatedAt`       | Last update timestamp                                |

### AuthAccount

A single login method attached to a `User`. One identity may hold multiple
providers (for example `CREDENTIALS` + `GOOGLE`).

| Field                     | Notes                                          |
| ------------------------- | ---------------------------------------------- |
| `id`                      | UUID v7                                        |
| `userId`                  | Owner (`ON DELETE CASCADE`)                    |
| `provider`                | `AuthProvider` enum: `CREDENTIALS` \| `GOOGLE` |
| `providerAccountId`       | Provider's stable subject id                   |
| `passwordHash`            | Nullable; set only for `CREDENTIALS`           |
| `createdAt` / `updatedAt` | Timestamps                                     |

`providerAccountId`:

- **GOOGLE** — the OIDC `sub` (stable subject identifier), **not** the email
  address.
- **CREDENTIALS** — the normalized email. Credentials login is by email, so the
  normalized email is the account identifier.

Constraints:

- `UNIQUE (provider, providerAccountId)` — one provider account belongs to one
  user.
- `UNIQUE (userId, provider)` — a user has at most one account per provider.

### AuthSession

Server-side session/refresh record. Short-lived access tokens plus
server-controlled refresh state (token issuance is a later task).

| Field              | Notes                             |
| ------------------ | --------------------------------- |
| `id`               | UUID v7                           |
| `userId`           | Owner (`ON DELETE CASCADE`)       |
| `refreshTokenHash` | Only a hash is stored; **unique** |
| `createdAt`        | Session creation                  |
| `expiresAt`        | Expiry                            |
| `lastUsedAt`       | Optional last-use marker          |
| `revokedAt`        | `null` = active; set = revoked    |

Indexes: `userId` (user-wide revocation), `expiresAt` (expiry cleanup/lookup).

Single-active-session readiness: the schema supports invalidating a user's
active sessions (set `revokedAt`) and efficiently querying active sessions. The
one-active-session rule itself is business logic for a later task, so no DB
constraint enforces it here.

### EmailVerificationToken

| Field        | Notes                                      |
| ------------ | ------------------------------------------ |
| `id`         | UUID v7                                    |
| `userId`     | Owner (`ON DELETE CASCADE`)                |
| `tokenHash`  | Only a hash is stored; **unique**          |
| `createdAt`  | Issued at                                  |
| `expiresAt`  | Expiry                                     |
| `consumedAt` | `null` = usable; set = single-use consumed |

An index on `userId` supports invalidating older tokens on resend.

### PasswordResetToken

Same shape as the verification token but a **separate table**: verification and
reset tokens are never interchangeable.

| Field        | Notes                                      |
| ------------ | ------------------------------------------ |
| `id`         | UUID v7                                    |
| `userId`     | Owner (`ON DELETE CASCADE`)                |
| `tokenHash`  | Only a hash is stored; **unique**          |
| `createdAt`  | Issued at                                  |
| `expiresAt`  | Expiry                                     |
| `consumedAt` | `null` = usable; set = single-use consumed |

## Key decisions

- **ID strategy:** UUID v7 (`@default(uuid(7))`) for every auth model — one
  consistent, time-ordered, non-guessable identifier with good index locality.
- **Email normalization:** `trim` + `lowercase` only. No provider-specific
  rewriting (no Gmail dot or plus-address folding), which could merge distinct
  addresses. Uniqueness is enforced through the stored `emailNormalized` unique
  column, not through hidden database behavior. The original `email` is kept for
  display and delivery.
- **Password hash placement:** nullable `AuthAccount.passwordHash`, set only for
  the `CREDENTIALS` provider. The hash is never stored on `User`. Plaintext,
  reversible, or hint storage is prohibited.
- **Provider uniqueness:** both `(provider, providerAccountId)` and
  `(userId, provider)` are unique, preventing duplicate equivalent accounts.
- **Account linking:** structurally possible — one `User` can own a
  `CREDENTIALS` and a `GOOGLE` `AuthAccount`. Linking **logic** is not
  implemented and must never auto-link on an untrusted email claim; linking on a
  provider-verified email is a future, explicitly-decided flow.
- **Tokens:** only hashes are stored (`refreshTokenHash`, `tokenHash`).
  Single-use is represented by `consumedAt`; expiry by `expiresAt`.
- **Cascade:** deleting a `User` cascades to all auth-owned children
  (accounts, sessions, tokens). Authentication records do not outlive their
  identity.

## Deliberately not modeled (A-001)

`Customer`, `Address`, `Order`, `Cart`, roles/permissions, and any commerce or
authorization state. Also omitted to avoid speculative data collection:
session `userAgent`/`ipAddress` (add only when a concrete requirement exists).

## Credentials registration (A-002)

`POST /api/auth/register` creates a credentials identity. Only login,
access-token, refresh, logout, email, reset, and OAuth flows remain
unimplemented.

### Request

```json
{ "email": "user@example.com", "password": "..." }
```

Body validation uses the project's Zod pipeline (global `ZodValidationPipe`,
`nestjs-zod`) with a `.strict()` schema: unknown fields are **rejected** (400),
not stripped. This keeps a single schema-validation approach (the same Zod used
for configuration).

- **Email:** required string, trimmed, valid format, maximum 254 characters.
  Original casing is preserved on `User.email`; `user@example.com`.
- **Password:** required string, **12–128 characters**. No composition rules
  (uppercase/digit/symbol) and no truncation — passphrases are accepted. The
  upper bound limits hashing resource abuse.

### Flow

```text
validate (DTO)
→ normalize email (trim + lowercase)
→ hash password (PasswordHasher / Argon2id)
→ transaction:
     create User (emailVerifiedAt = null)
     create CREDENTIALS AuthAccount
→ return safe registration response
```

`User` and `AuthAccount` are created in a single Prisma transaction, so a
failure never leaves a partial identity.

### Credentials account

```text
provider          = CREDENTIALS
providerAccountId = emailNormalized
passwordHash      = Argon2id digest (never plaintext)
```

`passwordHash` is only ever set for `CREDENTIALS`. The database schema cannot
express this cross-column rule (Prisma does not model `CHECK` constraints), so
the invariant is enforced in application code (`AuthService`) and covered by
tests. A database `CHECK` constraint is deliberately deferred to avoid a
schema hack not tracked by Prisma.

### Duplicate email

The normalized-email unique constraint is the authoritative protection — there
is no check-then-insert race. A Prisma `P2002` unique violation maps to
`409 Conflict` with the message `Email already in use`; no database constraint
names, Prisma internals, or stack traces are exposed. Concurrent registrations
of the same normalized email result in exactly one identity.

### Password hashing

- **Algorithm:** Argon2id (`@node-rs/argon2`).
- **Parameters (baseline, OWASP minimum):** memory `19456` KiB (19 MiB), time
  cost `2`, parallelism `1`.
- Digests embed the algorithm and parameters
  (`$argon2id$v=19$m=19456,t=2,p=1$...`), so `verify` can still check older
  digests after parameters are raised later.
- Hashing is behind a `PasswordHasher` interface (`PASSWORD_HASHER` token), so
  the Auth domain never depends on the hashing library directly.

### Response

`201 Created`:

```json
{ "id": "<uuid>", "email": "user@example.com", "emailVerified": false }
```

The response is intentionally small. `passwordHash`, account internals, session
data, and raw Prisma objects are never returned; no tokens are issued here.

### Errors

| Status | Meaning                                             |
| ------ | --------------------------------------------------- |
| `400`  | Request validation failure (email/password/unknown) |
| `409`  | Email already in use                                |
| `500`  | Unexpected server/database failure (no internals)   |

## Tests

Schema invariants are covered by `apps/api/test/database/auth-schema.db-spec.ts`
and password hashing by
`apps/api/src/modules/auth/password/argon2-password-hasher.spec.ts`.
`apps/api/test/database/auth-registration.db-spec.ts` covers the registration

preservation, hash verification, validation failures, duplicate handling, and
concurrent-registration race behaviour.
